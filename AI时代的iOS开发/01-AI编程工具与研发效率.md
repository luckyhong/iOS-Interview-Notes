# 01 · AI 编程工具与研发效率

### 1. 面试官问"你平时怎么用 AI 辅助编程"，应该怎么回答？

要点：

- 不要回答"我全程用 AI 写代码"，也不要回答"我从来不用"——两者都会让面试官担心你的判断力或学习能力。
- 结构化地说清楚**在哪个环节用、为什么用、怎么验证结果**，比单纯罗列工具名更有说服力。
- 给出一个具体场景，而不是泛泛而谈。

一个相对完整的回答结构：

1. **信息检索 / 样板代码**：用 AI 快速生成某个不熟悉 API 的用法示例、SwiftUI 布局的初稿、单元测试的骨架，节省查文档和敲重复代码的时间。
2. **代码审查的第二双眼睛**：写完 PR 前，让 AI review 一遍，重点看并发安全、内存循环引用、边界条件，作为自己 review 之外的补充，而不是替代。
3. **不用的场景**：涉及业务核心逻辑、性能敏感路径（比如自定义 `Layout`、列表滚动优化）、以及任何需要对底层机制（Runtime、内存模型）有精确理解的代码，AI 建议仅作参考，最终实现和验证仍由自己负责。
4. **怎么验证**：AI 生成的代码一定跑测试、看 diff、必要时用 Instruments 验证性能，而不是编译通过就合并。

面试官真正想确认的是：你有没有清晰的"什么该交给 AI、什么必须自己把关"的边界感，这比工具本身用得熟不熟练更重要。

### 2. Xcode 自带的代码补全、Cursor、GitHub Copilot、Claude Code 这几类工具，在 iOS 开发里的定位差异是什么？

要点：

- **Xcode 的 Predictive Code Completion / Swift Assist**：内建在 IDE 里，基于当前工程上下文做行内补全，延迟低、集成度高，但生成范围一般局限在当前文件/局部上下文，多用于"补全"而非"生成整段方案"。
- **Cursor / GitHub Copilot 这类行内补全工具**：以 IDE 插件或独立编辑器形式存在，跨文件上下文理解更强，适合快速产出样板代码、重复模式代码（比如根据一个 Model 生成对应的 `Codable`、`Equatable`、SwiftUI `View`）。
- **Claude Code / Codex 这类 CLI/Agent 工具**：不是补全，而是能读工程结构、跨多个文件改动、自己跑构建和测试、根据报错继续迭代的"智能体"，适合处理"改一个跨模块的 bug""按需求做一次小规模重构"这种需要多步骤规划的任务，但也需要更强的 review 能力去确认它没有引入范围外的改动。

三者不是互斥关系，很多团队会同时用：日常敲代码用 IDE 内补全，遇到探索性/跨文件任务用 Agent 工具，PR 阶段再叠加一层 AI code review。面试时把这个分层说清楚，比单纯说"我用 XX 工具"更能体现你对研发流程的理解。

### 3. AI 生成的 Swift/SwiftUI 代码常见的坑有哪些？你怎么做 review？

要点（AI 生成代码最容易踩的几类坑）：

- **API 幻觉**：编出一个听起来合理但实际不存在的方法名或参数，尤其是较新的 SwiftUI/Swift Concurrency API，训练数据的时间滞后会放大这个问题。
- **过时写法**：给出基于旧版 Combine、`DispatchSemaphore` 甚至 `NSOperation` 的方案，而不是当前项目里已经统一使用的 `async/await` 或 `@Observable`。
- **并发安全问题**：在 Swift 6 严格并发检查下，AI 给出的代码经常缺少 `@MainActor` 标注，或者在闭包里直接捕获非 `Sendable` 类型，编译能过但会有数据竞争风险。
- **忽略项目既有约定**：比如项目统一用依赖注入 + 协议隔离网络层，AI 给的示例却是单例 + 强耦合，看起来能跑，但破坏了架构一致性。
- **过度设计**：为了"看起来完整"，生成一堆用不上的协议抽象层，增加不必要的复杂度。

Review 时可以按这个顺序检查：

1. 能不能编译，尤其是开启 Swift 6 严格并发检查后能不能过；
2. 是否引用了不存在或已废弃的 API（对着官方文档核实，不要凭印象）；
3. 是否符合项目现有的架构约定和命名规范；
4. 涉及主线程/后台线程切换、内存管理（闭包捕获 `self`）的地方要单独确认；
5. 关键路径补一段单元测试，用测试结果说话，而不是"看起来对"。

### 4. 如何用 AI 辅助提升测试覆盖率？

要点：

- AI 适合快速生成测试的**骨架和边界用例枚举**（比如空数组、极值、nil、并发调用），但测试断言的"预期值是否正确"必须由人来判断——AI 不知道你的业务规则。
- 对 `XCTest`/`Swift Testing`，可以让 AI 先分析一个函数的所有分支路径，生成对应的用例列表，再逐条确认是否需要、预期结果是否正确，避免手写时漏掉边界情况。
- UI 测试（`XCUITest`）可以让 AI 根据页面上的 `accessibilityIdentifier` 生成交互脚本初稿，但断言逻辑和等待策略（避免 flaky test）仍需人工打磨。
- 覆盖率数字本身不是目标，用 AI"刷"出来的高覆盖率如果都是无意义断言（比如只判断"没有崩溃"），面试官追问时很容易露馅，因此要能讲清楚每一类测试具体在验证什么。

### 5. AI 编程会不会让初级 iOS 工程师被淘汰？面试中如何回应这个问题？

要点：

- 不要正面回避，也不要过度焦虑地附和，给出一个基于观察的判断，而不是情绪化的立场。
- 一个站得住脚的角度：AI 淘汰的不是"初级工程师"这个身份，而是"只能完成明确指令、不具备判断力"的工作方式——这句话对初级和资深工程师同样成立。
- 结合自己的经历补一句实际观察，比如：借助 AI，一个人能覆盖的产出范围变大了，这意味着团队对"每个人"的期望值在提高，入门的门槛可能变高，但对能快速用 AI 补齐知识盲区、同时保有判断力的新人来说，成长曲线反而更陡（更快）。

参考详细展开见 [04·职业发展与面试软实力](04-职业发展与面试软实力.md) 的第 1 题。

### 6. "Prompt 工程"会成为 iOS 工程师的新技能项吗？

要点：

- 对于**用 AI 辅助写代码**这个场景，"prompt 工程"更多体现为：能不能给 AI 提供足够的上下文（相关文件、约束条件、期望的代码风格），以及能不能通过追问快速收敛到可用方案——这本质上是"清晰表达问题"的能力，和写清楚一个 Jira 需求单是同一种能力的延伸，不是一门孤立的新学科。
- 对于**把 LLM 能力集成进 App**这个场景（见 [03·大模型能力集成到 iOS App](03-大模型能力集成到iOS-App.md)），prompt 设计确实变成了产品/工程交叉的实际工作内容，需要考虑 token 成本、上下文裁剪、多轮对话的稳定性，这部分更接近"新技能"。
- 面试时把这两个场景分开说，能体现你对"用 AI"和"做 AI 功能"这两件事的区别有清晰认知，这本身就是一个加分点。
