# 03 · 大模型能力集成到 iOS App

这一部分是目前中大厂 iOS 面试里增长最快的考点：不再问"你知不知道有大模型这个东西"，而是问"如果让你在 App 里做一个 AI 对话功能，网络层、UI 层、安全性你分别怎么设计"。下面按实际工程链路拆解。

### 1. 怎么在 iOS 里实现流式（streaming）对话效果？

要点：

- 大模型接口通常以 **SSE（Server-Sent Events）** 或分块传输的方式，边生成边把文本片段（token）推给客户端，而不是等全部生成完再一次性返回。
- iOS 端用 `URLSession` 的 `bytes(for:)` 异步序列可以直接按行读取流式数据，不需要引入额外的 SSE 解析库：

```swift
func streamChat(request: URLRequest) async throws -> AsyncStream<String> {
    AsyncStream { continuation in
        Task {
            let (bytes, response) = try await URLSession.shared.bytes(for: request)
            guard let http = response as? HTTPURLResponse, http.statusCode == 200 else {
                continuation.finish()
                return
            }
            for try await line in bytes.lines {
                guard line.hasPrefix("data: ") else { continue }
                let payload = line.dropFirst(6)
                if payload == "[DONE]" { break }
                if let delta = parseDelta(payload) {
                    continuation.yield(delta)
                }
            }
            continuation.finish()
        }
    }
}
```

- UI 侧接住这个 `AsyncStream`，每收到一个片段就追加到当前显示的字符串上。SwiftUI 里要注意：频繁的小颗粒度状态更新可能导致每个字符都触发一次 view 重新渲染，出现"打字机效果卡顿"，常见优化是**攒够一小段（比如几十毫秒或若干字符）再统一 setState 一次**，而不是每个 token 都立即刷新。
- 一定要支持**取消**：用户离开页面或手动停止生成时，要能取消对应的 `Task`/`URLSessionTask`，否则请求会一直挂着消耗资源和 token 费用。

### 2. 如何设计一个支持流式、可取消、可重试、能兼容多个大模型服务商的网络层？

要点：

- **协议先行**：定义一个和具体厂商无关的抽象，比如 `ChatProviding`，输入统一的消息结构，输出统一的 `AsyncThrowingStream<ChatDelta, Error>`，各厂商（OpenAI 协议、Claude 协议、自建网关）各自实现一个 adapter，业务层完全不感知底层是谁在提供服务。
- **统一错误处理**：不同厂商的限流、鉴权失败、内容审核拦截等错误格式都不一样，adapter 层要把它们归一化成几类客户端可以统一处理的错误（网络错误、鉴权错误、限流、内容策略拒绝、未知错误），上层 UI 才能给出恰当的提示而不是裸露原始 error message。
- **可取消**：每次请求持有对应的 `Task`，暴露一个 `cancel()`，取消时要同时终止底层网络连接，避免流式连接空转。
- **重试策略**：区分"可重试错误"（网络抖动、超时）和"不可重试错误"（鉴权失败、内容被拒绝），只对前者做指数退避重试，且要注意流式请求如果已经收到部分内容，重试通常意味着重新开始一次完整对话，而不是"续传"，这一点要在产品层面想清楚展示逻辑。
- **实际不建议**客户端直接持有多个厂商的 API Key 各自直连（见第 6 题的安全性问题），更常见的做法是客户端只对接自己的后端网关，由网关统一代理转发、做鉴权和限流，adapter 抽象这一层放在网关侧或客户端侧都可以，取决于团队架构。

### 3. 多轮对话的上下文在客户端应该怎么存储和管理？

要点：

- **Token 是有限资源**：大模型对话有上下文长度上限，多轮对话不能无限累加历史消息发送给服务端，需要做**上下文裁剪**——常见策略是保留最近 N 轮 + 一份对更早对话的摘要（摘要本身也可以调用一次模型生成）。
- **本地持久化**：对话记录通常用轻量级本地数据库（`SwiftData` / `Core Data` / SQLite）存储，要考虑单条消息可能很长（流式生成的完整文本）、附件（图片）的存储方式，以及历史会话列表的分页加载。
- **Token 计数**：为了准确裁剪上下文和预估成本，客户端有时需要一个近似的 tokenizer 来估算一段文本的 token 数（不同模型的分词规则不同，客户端通常只做近似估算，精确计数依赖服务端返回的 usage 字段）。
- **草稿态与最终态**：流式生成过程中的文本是"进行中"状态，用户中途取消或生成失败时，要明确这条消息在本地存储里是保留部分内容、标记为"已中断"，还是直接丢弃，这个产品细节经常被面试官追问，因为它体现你有没有真正做过这类功能。

### 4. 多模态输入（图片、语音）在 iOS 端怎么处理？

要点：

- **图片输入**：多数视觉大模型接口接收 base64 编码的图片或图片 URL。客户端要注意在上传前做**压缩和尺寸限制**（原图直接编码成 base64 体积会非常大，既浪费流量也可能超出接口限制），一般会 resize 到模型建议的最大边长，再选择合适的压缩质量。
- **语音输入**：常见链路是"端侧或云端语音转文字（ASR）→ 文字进入大模型对话流程"，iOS 端可以用系统自带的 `Speech` 框架做本地语音识别，减少一次网络往返；如果产品需要更高准确率或多语言支持，也可能调用云端 ASR 服务。
- **语音输出（TTS）**：把大模型返回的文本转成语音播放，端侧可以用 `AVSpeechSynthesizer` 做基础的系统 TTS，效果自然度有限；更拟人的音色通常依赖云端 TTS 服务，此时又要回到"流式文本 → 分句 → 流式请求 TTS → 边收到音频边播放"这样的流水线设计，避免等全部文字生成完才开始合成语音。
- **权限与体验**：麦克风、相册权限的申请时机、拒绝后的引导文案，这些看似基础的细节在"AI 功能"的语境下经常被面试官用来考察你是否具备完整的产品思维，而不只是"调通接口"。

### 5. RAG（检索增强生成）方案里，iOS 客户端能做什么，不能做什么？

要点：

- **典型 RAG 流程**：用户问题 → 向量化 → 在向量数据库里检索相关文档片段 → 把检索结果拼进 prompt → 交给大模型生成答案。这个流程里**向量数据库的检索和大规模 embedding 计算通常在服务端完成**，因为向量库需要维护大规模索引、做相似度检索，这不是移动端的强项。
- **客户端能做的事**：
  - 收集/编辑要检索的原始内容（比如用户本地笔记、文档），上传给服务端建索引；
  - 做一个**小型本地知识库**场景（比如个人的少量笔记、聊天记录），用轻量的本地 embedding 模型（可以基于 Core ML 部署一个小型 embedding 模型）配合简单的向量相似度计算（余弦相似度，量级小的话直接线性扫描即可，不需要专门的向量索引结构），实现完全离线的"本地 RAG"，这类场景近几年逐渐出现在强调隐私的效率类 App 里；
  - 展示检索到的引用来源（比如"以下回答参考了你的第 3 篇笔记"），这是纯前端交互层面的工作。
- **不建议客户端做的事**：把大规模文档的 embedding 生成和检索完全放在端侧——数据量一大，端侧算力和存储都会成为瓶颈，除非产品场景本身就限定为"少量本地私有数据"。

### 6. AI 接口的安全性要注意什么？为什么不能把 API Key 硬编码在客户端？

要点：

- App 的二进制文件可以被反编译或抓包，任何硬编码在客户端的 API Key、密钥都可能被提取出来，一旦泄露，攻击者可以拿着你的 Key 无限调用付费的大模型接口，产生高额费用（这类事故在行业里已经发生过多次）。
- 正确做法是客户端**不直接持有大模型服务商的 Key**，而是请求自己的后端网关，由网关持有真正的密钥、代理转发请求，同时在网关层做用户鉴权、限流、审计。
- 网关层还应该承担的职责：**内容安全审核**（防止被用来生成违规内容）、**用量控制**（防止单个账号异常调用产生刷量攻击）、**Prompt 层面的防护**（比如防止用户输入被设计成"越狱"系统 prompt、窃取你精心设计的系统级 prompt 内容）。
- 面试里如果直接被问"客户端怎么调大模型 API"，第一句话就应该是"客户端不直连，通过自己的网关转发"，这是这类问题里最容易体现工程安全意识的加分点。

### 7. Function Calling（工具调用）在客户端应该怎么设计交互？

要点：

- Function calling 的本质是：大模型判断"这个问题需要调用某个具体功能才能回答"，返回一个结构化的函数名 + 参数（而不是直接返回自然语言答案），客户端负责真正执行这个函数（比如查天气、查订单、操作 App 内某个功能），再把执行结果回传给模型，让它基于结果生成最终的自然语言回答。
- 客户端设计上通常需要：
  - **一个函数注册表**，明确声明每个可被模型调用的功能的名称、参数 schema、以及实际执行的代码，这部分和 [App Intents](02-苹果端侧AI技术栈.md) 的意图声明思路上是相通的——都是把"App 能做的事"结构化地暴露出去；
  - **执行前的用户确认机制**：涉及有副作用的操作（发消息、下单、删除数据），出于安全和体验考虑，通常不能让模型"静默执行"，而要在 UI 上明确展示"AI 打算执行 XX 操作"，等用户确认后再真正调用；
  - **执行结果的可视化**：把函数调用的中间过程（正在查询、查询结果）呈现给用户，而不是让用户只看到一段"黑箱"生成的最终文字，这对建立用户信任很重要，也是目前主流 AI 类 App 在交互设计上的共同趋势。
